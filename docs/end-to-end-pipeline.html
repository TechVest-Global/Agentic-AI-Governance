00 Orientation & map

The platform is a FastAPI backend (backend/app) with a Vite/React frontend. An audit is one EvaluationRun row driven through eight phases by a single background job. Everything a phase learns is written append-only before the next phase reads it, so a run is reconstructable from the database alone.

The two entry points

backend/app/main.py → create_app() mounts api/router.py under /api/v1, installs the exception handlers, CORS, and a bearer-token middleware that protects POST/PUT/PATCH/DELETE only (GET stays open so the SSE progress stream and <img> media routes work without headers). On startup it also spawns a daemon thread running reconcile_interrupted_runs() — see § Failure & resume.

Phase & status vocabulary

Two enums in models/enums.py track progress. RunPhase is the ordered pipeline position; RunStatus is the lifecycle state (and what clients poll for a terminal value).

01 App registry — registering the system under audit

Nothing can be audited until it exists in the registry. Registration turns one nested payload into ~16 normalized fact tables in a single transaction, derives a preliminary risk tier, and — critically for the engine — creates one AISystemCapability per endpoint. Those capability rows are what every later phase treats as the audit surface. 

POST /api/v1/ai-systems/register
└─ api/routes/ai_systems.py :: register_ai_system()

      ├─ _first_duplicate() ×4          # reject dup model/endpoint/framework/control BEFORE insert

      │

      ├─ _build_usage_context()         → ai_system_usage_contexts
      ├─ _build_context_profile()       → application_context_profiles  # 5 seeded sections

The four engine-facing fields

Most registration data is documentation. Four fields on AISystem are load-bearing for the pipeline:

FieldSet fromRead by

Capabilities, and how they get richer

_build_capability_for_endpoint() creates a minimal capability (type inference, modality defaulting to text, no input schema). Two routes enrich them, and both matter downstream:

  • POST /ai-systems/{id}/capabilities/import-from-catalog → services/capability_import.py fetches GET {target_endpoint_ref}/catalog and creates one capability per endpoint with its real input_schema and modality.
  • PATCH /ai-systems/{id}/capabilities/{cid} for hand edits.
Why the schema matters

input_schema and modality drive the two fail-closed gates in _execute_probe_plan(). Without them a probe against an image endpoint is skipped as text-only, and a probe against a document-consuming endpoint is skipped because the question would be parsed as the document. A capability with no schema silently reduces probe coverage — see § 07.

Retrieval context

POST /ai-systems/{id}/retrieval-context[/upload] ingests a corpus (PDF via pypdf, DOCX via python-docx, or pasted text — _extract_document_text()). RAGAS/DeepEval grounding metrics read it; without it they skip with a reason rather than fabricate a hallucination score (missing_grounding_corpus_reason()).

03 Layer 1 — Context assembly

Fully deterministic: no LLM, no wall clock, no randomness. Same input always yields the same output, which is what lets the result be hash-chained and reproduced.

Read back

GET /evaluation-runs/{id}/context-assembly → get_latest_context() rebuilds the same object from the highest-sequence context_assembled state entry. 404 if the phase never ran.

Why logs are synthesized

With no logs, total_requests: 0 tripped the empty branch of every requirement, producing an identical "everything missing" gap set on every run — and since coverage gaps are the planner's only per-run variable, the planner then allocated an identical budget every time and looked static. The synthesizer gives each system its own partial, plausible sample instead.

Two-stage selection. A deterministic pass decides the candidate metric set from applicability filters; an LLM review pass may then narrow it — never widen it, and never by more than half.

06 Metric execution — the deterministic evidence layer

Twelve real evaluators score the planned metrics by probing the live target. Every metric produces exactly one EvidenceRecord and one MetricResult, committed the moment it is built — because the probe already happened whether or not the process survives to persist it.

├─ plan = build_metric_plan()

│     # up front, so live watchers see the layer activate before slow evaluators run

│  # attribute, and concurrent lazy refreshes from workers raise
│  # "session is provisioning a new connection; concurrent operations not permitted"
│  with Session(engine) as snapshot_session:
│     worker_ai_system      = snapshot.get(AISystem, id)

│  metrics      = [m for m in plan.metrics if m.metric_id not in already_done]

│  # bounded LOW: at 6 the shared Azure judge returned a 429 storm and backoff

│     ├─ gateway.bind_log_capture(capture_buffer, agent_name=metric.tool_name)

│     │     # pool threads are reused

07 Layer 3 — Specialist agents

Seven model-backed agents run in two stages: six fan out concurrently, then risk_scorer runs after a barrier so it sees a complete peer finding set. Each agent probes the live target, optionally calls a real evidence tool, reasons over both with the governance model, and returns findings.

Phase setup

The router's four exits

OrderConditionExitEffect
1sufficientactionBreak; proceed to Layer 5 at the verdict's own tier
1bnot remediableactionInsufficient but conclusive — a failed metric can't be cleared by any remediation path, so decide now
2iteration >= 3exhaustedForce blocked / human_review + build_exhaustion_memo()
3otherwiseremediatere_deliberate · re_probe · re_plan
Why exit 1b exists

No remediation path re-runs metric execution, so once a metric has conclusively failed the sufficiency gate (failed == 0) can never be satisfied. The loop used to run to its cap anyway and stamp the verdict with a memo reading "unresolved uncertainty: the Council lacked enough evidence to decide" — the opposite of the truth. Exit 1b decides in one iteration and says so positively: DECIDED ON CONCLUSIVE EVIDENCE. An error metric stays remediable, because there the evidence is missing, not negative.

       ├─ else _enter_cooldown(retry_after or 2**attempt)   # EXTENDS, never shortens
       └─ non-retryable → _append_log(status="error"|"rate_limited", attempts=0 if
              quota-latched else attempt+1, error_type, error_detail,
              prompt_text kept, response_text=None) → raise

GatewayGovernanceModelClient.complete() mirrors this without the throttle/cooldown, logging call_type: "governance" and keeping prompt_text even when the call fails — a failed governance call is exactly when a reviewer needs to see what was asked.

· Integrity — two hash chains and a content digest

State chain

governance_state_entries — one entry per phase artifact. append_state_entry() hashes {run_id, sequence_number, entry_type, source, phase, payload, previous_hash} as canonical JSON (sorted keys, compact separators). UNIQUE(run_id, sequence_number).

Audit ledger

audit_ledger_entries — one entry per governance event. append_ledger_entry() hashes {run_id, event_type, actor_type, actor_id, payload, previous_hash}. commit=False folds an entry into a caller's transaction.

Content digest

services/content_integrity.py — SHA-256 over the exact Finding / MetricResult rows a ledger entry summarized, at write time. The chains prove the ledger rows weren't altered; the digest catches changes to the ordinary mutable tables they describe.

Both verifiers walk the whole chain unpaginated and return the first breach: sequence_gap, previous_hash_mismatch, or entry_hash_mismatch. There is a matching invariant suite in services/audit_invariants.py.

Startup reconciliation

main.py @app.on_event("startup") → daemon thread → reconcile_interrupted_runs(session)
  # On a THREAD because reconciliation RESUMES a run — real probes, minutes of work.
  # Inline it sat in front of the socket bind ("Waiting for application startup",
  # port never opened), and a mid-resume death faced the next boot with the same
  # unfinished run — an unbounded restart loop that never served a request.

SELECT EvaluationRun WHERE status IN (_INTERRUPTED_STATUSES + degraded)
   _INTERRUPTED_STATUSES = created · context_assembly · planned ·
                           metrics_running · agents_running · council_running
for run in stuck:
├─ degraded and _is_interrupted_degraded(run) is False → skip
│     # degraded + current_phase == completed means the run genuinely finished;
│     # the phase is what tells the two kinds of degraded apart
├─ is_awaiting_plan_approval(run) → skip   # waiting on a person, not a crash
├─ a Verdict exists → the council was reached → mark completed (or keep degraded),
│                     phase=completed, result_summary["reconciled"]
├─ status ∈ {created, context_assembly} → run_governance_pipeline() from scratch
│     # no plan was ever persisted; context assembly makes no target calls, so
│     # retrying it has no side effects
├─ otherwise → resume_governance_pipeline()
│     # run_metrics skips already passed/failed metrics; run_agents skips
│     # already-completed non-remediation agents — no probe is repeated
└─ resume itself raised → status=failed, error_summary["context"] = "Resume attempt
     after worker restart failed." + ledger "run.reconcile_failed"

One SSE subtlety

Each 2-second tick opens its own short-lived session. Looping on the request-scoped session made its identity map keep returning the first snapshot of the run row — status and phase never advanced, the progress bar froze at whatever phase the stream connected during, a terminal status was never observed, and a pool connection stayed pinned for the run's lifetime.
